# Cherrypicker 실사용 작업

## 상태 규칙

- `[ ]`: 일반 대기
- `[-]`: 현재 진행 중
- `[>]`: 사용자가 승인한 단 하나의 다음 작업
- `[~]`: 보류. 다시 활성화하기 전에는 진행하지 않음
- `[x]`: 완료 조건을 모두 검증한 작업

작업을 시작할 때 `[>]`를 `[-]`로 바꾸고, 완료 조건을 모두 관찰·실행한 뒤에만 `[x]`로 바꾼다. 후속 작업을 확정했을 때만 하나의 `[>]`를 새로 지정한다.

## 현재 기준선

로그인 없는 로컬 workspace, 공용 카탈로그, 조합 추천, 결제 기록, 선택적 계정 동기화, 카드·프로모션 수집·검수·revision·rollback 기반은 이미 구현되어 있다. 아래 목록은 이 기반을 재구축하는 작업이 아니라 비공개 실사용까지 남은 사용자 흐름을 완성하는 순서다.

  - 할인형·적립형과 등급 variant를 분리하고 공식 브랜드별 usage group으로 공유 횟수·금액 한도를 집계한다. CU의 할인·적립 `1일 1회`, 등급별 일 한도, 1천 원 최소·단위 계산과 상품·매장 제외 조건을 구조화했으며 공차 상품 범위와 이마트·CGV·11번가 복합 혜택의 보수적 정보 처리를 회귀 테스트로 고정했다.
  - 신규·변경 SKT 후보는 상세 문서의 필드별 근거가 있어도 사람 검수 전에는 게시하지 않는다. 미게시 후보가 발견한 브랜드도 승인 전 공용 브랜드 목록에 넣지 않는다. 실시간 수집과 AI 검증은 읽기 전용으로 실행했으며 후보 DB 반영·대량 게시는 실행하지 않았다.
  - 규칙 parser가 후보를 만들지 못한 13개 브랜드만 OpenAI structured output으로 보조 구조화한다. 모든 원문 variant, strict schema와 필드별 원문 인용을 검증하고 input hash cache, 실행당 15건·브랜드당 24,000자 기본 상한을 적용한다. 원문에 없는 숫자는 계산값에서 제거하고 필요한 경우 `INFORMATION_ONLY`로 낮추며, 검증 실패는 전체 호출 상한 안에서 브랜드당 최대 2회까지만 피드백 재시도한다. 키 부재·호출 또는 검증 실패 시 SKT 전체를 `PARTIAL`로 낮춰 기존 게시본과 삭제 판정을 보호한다.
  - 로컬 Luna 실 API로 공개 원문 10개 목록·182개 상세(10.74 MiB)를 전수수집했다. 규칙 parser 169개 브랜드·404개 후보와 AI 보완 13개 브랜드·26개 후보를 합쳐 182개 브랜드·430개 후보를 모두 구조화했고, 후보 감사 차단·미해석 브랜드·자동 게시가 각각 0건이었다. 같은 원문 재수집은 13개 브랜드 모두 input hash cache에 적중해 추가 AI 호출 없이 같은 430개 후보를 반환했다. CU 할인·적립 4개 후보도 `dailyCount: 1`과 등급별 일 한도를 유지했다.
  - 전체 439개 테스트, lint, TypeScript 검사, production build, diff 형식 검사와 기존 migration 적용을 통과했다. AI 경로는 모의 provider로 성공·재시도·원문 밖 인용 거부·근거 없는 숫자의 정보용 강등·hash cache·키 부재 부분 수집을 검증했고, 로컬 실 API 결과도 전체 감사를 통과했다. Chrome 1200×774와 360×800에서 T멤버십 유형·등급 선택, 미완료 진행 잠금, 저장·복원, 가로 넘침과 44px 터치 타겟을 검증했다.
