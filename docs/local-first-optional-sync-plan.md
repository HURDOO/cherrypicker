## 1. 결정 요약

Cherrypicker의 일반 사용자 경험을 다음 방향으로 전환한다.

1. 로그인 없이 앱을 열고 즉시 사용할 수 있다.
2. 개인 데이터는 먼저 브라우저의 IndexedDB에 저장한다.
3. 서버가 매일 수집·파싱·검수한 최신 혜택 카탈로그를 브라우저가 받아 캐시한다.
4. 추천 계산은 최신 카탈로그와 로컬 개인 데이터를 사용해 브라우저에서 수행한다.
5. 계정은 앱 사용 조건이 아니라 백업과 여러 기기 동기화를 원하는 사용자를 위한 선택 기능으로 제공한다.
6. 프로모션 수집·검수용 관리자 인증은 일반 사용자 로그인과 별개로 계속 보호한다.

핵심 제품 문구는 `로그인해야 쓰는 서비스`가 아니라 `이 기기에 저장되며, 로그인하면 백업·동기화할 수 있는 앱`이다.

## 2. 목표와 비목표

### 목표

- 첫 방문에서 회원가입과 로그인 장벽 제거
- 서버 또는 네트워크 상태와 무관한 빠른 추천 계산
- 마지막으로 받은 카탈로그를 이용한 제한적인 오프라인 사용
- 매일 갱신되는 공용 혜택 정보와 개인 데이터의 명확한 분리
- 나중에 계정 동기화를 추가해도 데이터 모델을 다시 깨지 않도록 준비
- 현재 운영 데이터와 추천 정확도를 보존하며 단계적으로 전환

### 당장 하지 않는 것

- 프로모션 수집기와 관리자 검수 기능의 브라우저 이전
- 첫 단계부터 복잡한 실시간 협업 또는 다중 사용자 편집 지원
- 첫 단계부터 카탈로그 증분 패치 프로토콜 구현
- 검증 없이 기존 인증·API·SQLite 사용자 데이터를 즉시 삭제
- 공개 배포나 운영 DB 파괴적 마이그레이션

## 3. 전환 전 기준선

현재 일반 사용자 흐름은 다음과 같다.

- `src/proxy.ts`가 홈·설정·내역을 로그인 필수 경로로 보호한다.
- `src/hooks/useAppData.ts`가 Better Auth 세션을 확인한 뒤 `/api/app-data`를 호출한다.
- 카드, 규칙, 혜택 프로필, 실적과 결제 기록은 SQLite에서 `userId`로 분리한다.
- 홈의 입력이 바뀌면 300ms debounce 후 `/api/recommendations`를 호출한다.
- `src/lib/recommendation-server.ts`가 서버 데이터들을 모아 `calculateBestCombinations()`를 실행한다.
- 브랜드 탐색 즐겨찾기와 위치 기반 방문 기록만 현재 `localStorage`에 저장한다.

2026-08-18 개발 DB에서 확인한 대략적인 규모는 다음과 같다.

- 카테고리 10개
- 브랜드 277개
- 카드 8개
- 카드 규칙 81개
- 게시 프로모션 252개
- 한 브랜드에 매칭되는 게시 프로모션 최대 7개
- 게시 프로모션의 주요 JSON·문자열 필드 합계 약 258KB

현재 규모에서는 브라우저 계산이 충분히 가능하다. 다만 `enumerateOfferSubsets()`가 혜택 부분집합을 열거하므로 한 브랜드의 중첩 가능한 혜택 수가 크게 증가할 때를 대비한 후보 수 제한과 성능 측정이 필요하다.

## 4. 목표 아키텍처

```text
공식 페이지/API
      |
      v
서버 수집 -> 파싱/분류 -> 관리자 검수 -> 게시 카탈로그 snapshot
                                               |
                                     ETag/version 확인
                                               |
                                               v
                                    브라우저 IndexedDB
                                    - 최신 카탈로그
                                    - 개인 workspace
                                               |
                                               v
                                    브라우저 추천 계산
                                               |
                              선택적으로 로그인한 경우만
                                               v
                                      계정 동기화 API
```

서버는 공용 정보의 신뢰 가능한 공급자이고, 브라우저는 개인화·저장·추천 계산의 기본 실행 환경이다. 계정 서버는 로그인한 사용자의 개인 데이터 복사본과 변경 이력만 보관한다.

## 5. 데이터 소유권 경계

### 서버 권위 데이터: 공용 카탈로그

- 시스템 카테고리와 브랜드
- 시스템 카드와 카드 혜택 규칙
- 프로모션 제공자
- 게시 상태의 프로모션
- 구독 상품 카탈로그
- 가맹점 승인 경로 검증 정보
- 카탈로그 버전과 생성 시각

수집 후보 원문, 검수 큐, 내부 진단, 관리자 메타데이터는 공개 카탈로그에 포함하지 않는다.

### 브라우저 권위 데이터: 개인 workspace

- 사용자가 추가한 카테고리와 브랜드
- 사용자가 추가한 카드와 혜택 규칙
- 통신사·구독·페이·머니·포인트 혜택 프로필
- 월별 카드 실적
- 결제 기록과 당시 추천 조합 snapshot
- 즐겨찾기, 표시 순서, 주변 브랜드 방문 기록
- 로컬 schema 버전, 기기 ID, 동기화 cursor와 outbox

### 선택적 계정 동기화 데이터

로그인한 경우에만 개인 workspace 레코드를 계정에 연결한다. 클라이언트가 보낸 `userId`를 신뢰하지 않고 서버 세션에서 소유자를 결정한다. 공용 카탈로그는 계정 데이터에 복제하지 않는다.

## 6. 카탈로그 배포 계약

초기 버전은 매일 전체 snapshot을 게시하는 단순한 계약으로 시작한다. 현재 데이터 크기에서는 증분 패치보다 구현과 복구가 단순한 전체 snapshot이 적절하다.

예시 envelope:

```ts
interface BenefitCatalogSnapshot {
    schemaVersion: number;
    catalogVersion: string;
    generatedAt: string;
    freshness?: {
        collectionStatus: 'SUCCEEDED' | 'PARTIAL' | 'FAILED' | 'UNKNOWN';
        sourceCount: number;
        failedSourceCount: number;
        lastAttemptAt?: string;
        lastSuccessfulAt?: string;
        lastPublishedAt?: string;
    };
    categories: Category[];
    brands: Brand[];
    cards: Card[];
    rules: BenefitRule[];
    providers: PromotionProvider[];
    subscriptionProducts: SubscriptionProduct[];
    promotions: PromotionOffer[];
    routeVerifications: MerchantRouteVerification[];
}
```

계약 원칙:

- `catalogVersion`은 계산 내용 기반 hash로 결정적이어야 하며 수집 시각만 바뀌면 유지한다.
- 수집 신선도 metadata가 바뀌면 내용이 같아도 ETag를 갱신해 클라이언트에 새 상태를 전달한다.
- 응답은 `ETag`를 제공하고 클라이언트의 `If-None-Match`에 `304`로 응답한다.
- 클라이언트는 새 snapshot의 schema와 참조 무결성을 검증한 뒤 IndexedDB에서 원자적으로 교체한다.
- 다운로드나 검증이 실패하면 마지막 정상 snapshot을 유지한다.
- 앱에 `마지막 혜택 업데이트 시각`을 표시하고 오래된 카탈로그임을 알릴 수 있어야 한다.
- 전체 snapshot에서 사라진 항목은 최신 카탈로그에서 제거된 것으로 취급한다.
- 과거 결제 기록은 당시 `catalogVersion`과 조합 snapshot을 보존하므로 새 카탈로그로 재해석하지 않는다.
- 시스템 엔터티 ID는 카탈로그 갱신 사이에 안정적으로 유지해야 한다.
- 카탈로그 읽기는 로그인 없이 가능하고 캐시 가능한 별도 endpoint로 둔다.

모바일 브라우저의 백그라운드 실행은 보장되지 않으므로 `매일 특정 시각에 기기가 알아서 갱신`하는 것에 의존하지 않는다. 서버 수집은 정기 실행하되 클라이언트는 앱 시작, 포커스 복귀, 사용자의 새로고침 시점에 버전을 확인한다.

## 7. 로컬 저장 모델

핵심 데이터에는 `localStorage` 대신 IndexedDB를 사용한다. 카탈로그와 개인 workspace는 논리적으로 분리해 카탈로그 교체가 개인 데이터를 건드리지 않도록 한다.

동기화 가능한 개인 레코드는 최소한 다음 메타데이터를 가진다.

```ts
interface SyncMetadata {
    id: string;          // 브라우저에서 생성한 UUID
    createdAt: string;   // ISO 8601
    updatedAt: string;   // ISO 8601
    deletedAt?: string;  // tombstone
}
```

추가 원칙:

- UUID는 `crypto.randomUUID()`로 클라이언트에서 생성한다.
- 현재 정수 자동증가 방식의 결제 기록에는 동기화용 UUID를 새로 도입한다.
- 삭제는 동기화가 끝나기 전에 물리 삭제하지 않고 tombstone으로 남긴다.
- IndexedDB schema migration을 버전별로 정의하고 실패 시 기존 DB를 보존한다.
- JSON 내보내기와 가져오기를 계정 동기화보다 먼저 제공해 복구 경로를 확보한다.
- `navigator.storage.persist()`는 best effort로 요청하되 영구 보존을 보장한다고 안내하지 않는다.
- 브라우저 origin이 바뀌면 다른 저장소가 되므로 운영 URL을 안정적으로 유지한다.
- 결제 기록에는 추천 결과, 적용 단계, 금액, `catalogVersion`을 snapshot으로 보존한다.

## 8. 브라우저 추천 계산

`src/utils/calculation.ts`와 `src/utils/combination.ts`의 순수 계산 코드를 공용 엔진으로 유지한다.

필요한 변경:

- `src/utils/combination.ts`의 `node:crypto` 기반 조합 ID를 브라우저 호환 결정적 ID로 교체한다. 이 ID는 보안 경계가 아니므로 입력 단계 ID를 안정적으로 직렬화한 경량 hash로 충분하다.
- 서버 DB 조회와 계산 입력 조립을 엔진 밖에 유지한다.
- 로컬 개인 데이터로 카드/프로모션 사용량 집계를 계산하거나 변경 시 증분 갱신한다.
- 카탈로그 갱신과 사용자 입력 변경 시 같은 입력에서 항상 같은 추천 결과가 나와야 한다.
- 결제 금액이 작아 혜택의 실질 가치가 낮은 경우에는 혜택 경쟁 대신 카드 실적 달성을 우선하는 선택지를 제공한다.
- 기존 서버 계산과 브라우저 계산을 같은 fixture로 비교하는 parity 테스트를 추가한다.

성능 원칙:

- 브랜드, 채널, 기간, 프로필로 프로모션을 먼저 필터링한다.
- 중첩 가능한 혜택 후보 수와 생성되는 조합 수에 안전 상한을 둔다.
- 현재 상위 30개 결과 제한은 유지하되 모든 후보 생성 후 자르는 비용도 측정한다.
- 목표 모바일 기기에서 p95 계산 시간을 기록한다.
- 메인 스레드 작업이 50ms를 넘으면 계산기를 Web Worker에 상주시켜 카탈로그는 한 번만 전달하고 이후 요청 입력만 보낸다.
- Worker 사용 여부와 무관하게 입력 변경 debounce와 오래된 계산 결과 무시 정책을 유지한다.

## 9. 선택적 계정과 동기화

### 사용자 경험

- 홈과 기본 설정은 로그인 없이 완전히 동작한다.
- 로그인 CTA는 강제 redirect 대신 설정의 `백업 및 기기 연동`에 둔다.
- 비로그인 상태에는 `이 기기에 저장됨`을 명시한다.
- 로그인 상태에는 마지막 동기화 시각과 오류 상태를 표시한다.
- 로그인 직후 로컬 데이터를 지우거나 서버 데이터로 덮어쓰지 않는다.

### 최초 로그인 병합

1. 계정 데이터가 비어 있으면 로컬 workspace를 업로드한다.
2. 로컬 데이터가 비어 있으면 계정 workspace를 내려받는다.
3. 양쪽 모두 데이터가 있으면 병합 결과를 만들고 사용자에게 합칠 것인지 확인한다.
4. 서버가 업로드를 승인하고 클라이언트가 다시 읽어 검증할 때까지 로컬 원본을 유지한다.

### 기본 충돌 규칙

| 데이터 | 식별 기준 | 기본 병합 규칙 |
|---|---|---|
| 결제 기록 | UUID | append/union, 동일 ID는 최신 수정본 |
| 월별 실적 | 카드 ID + 실적 월 | `updatedAt`이 최신인 값 |
| 혜택 프로필 | 단일 profile 문서 | 최신 수정본, 이후 필요하면 필드 단위 병합 |
| 개인 카드·규칙·브랜드·카테고리 | UUID | 최신 수정본, tombstone 우선순위 명시 |
| 즐겨찾기·정렬 | preference 문서 | 초기에는 최신 문서 전체 적용 |

서로 참조하는 개인 카테고리 → 브랜드 → 카드/규칙은 같은 sync batch에서 참조 순서와 무결성을 검증한다.

### 동기화 프로토콜 최소 요구사항

- 각 변경 작업에 재시도 가능한 고유 `operationId`를 부여한다.
- push는 멱등이어야 한다.
- 서버는 계정별 단조 증가 revision 또는 변경 cursor를 발급한다.
- 클라이언트는 마지막 cursor 이후 변경을 pull한다.
- 실패한 변경은 IndexedDB outbox에 유지하고 지수 backoff로 재시도한다.
- 서버 시각만으로 동시성 전체를 판단하지 말고 revision을 함께 사용한다.
- 서버는 payload 크기, 레코드 수, 참조 무결성을 검증한다.
- 동기화된 로컬 데이터는 추천 계산의 권위 데이터로 계속 사용한다.

### 로그아웃과 계정 삭제

- `로그아웃하고 이 기기 데이터 유지`와 `이 기기 데이터도 삭제`를 구분한다.
- 기본 로그아웃은 동기화만 중지하고 로컬 데이터 유지 여부를 명확히 안내한다.
- 계정 삭제는 서버 복사본 삭제와 로컬 복사본 삭제를 별도 선택으로 다룬다.
- 공용 또는 분실 기기에서는 로컬 삭제 기능을 쉽게 찾을 수 있어야 한다.

구현된 로그아웃과 계정 삭제 대화상자는 로컬 유지를 기본값으로 사용한다. 로컬 완전 삭제는 프로필·카드·실적·결제 기록뿐 아니라 tombstone과 sync state/outbox를 지우고 새 workspace·device ID를 만든다. 계정 삭제는 현재 비밀번호와 `계정 삭제` 확인 문구를 모두 요구하며, Better Auth 사용자 삭제의 cascade로 인증 정보와 계정 snapshot·operation도 제거한다.

## 11. 롤아웃과 데이터 안전

- 브라우저 계산과 로컬 저장은 처음에 feature flag 또는 개발 전용 이중 실행으로 도입한다.
- 운영 데이터 import가 검증되기 전에는 기존 서버 레코드를 삭제하거나 schema에서 제거하지 않는다.
- 기존 계정 데이터의 로컬 import는 반복 실행해도 중복되지 않아야 한다.
- 클라이언트 migration 실패 시 빈 DB를 새로 만들지 말고 오류와 export/복구 경로를 제공한다.
- 새 카탈로그가 손상되면 마지막 정상 카탈로그로 즉시 돌아갈 수 있어야 한다.
- 서버 수집 실패는 기존 게시 snapshot을 제거하지 않는다.
- 운영 migration과 배포는 이 계획 문서만으로 자동 승인되지 않으며 기존 배포·backup 절차를 따른다.

## 12. 검증 기준

### 기능

- 로그인하지 않고 카드/프로필/실적을 설정하고 추천을 받을 수 있다.
- 네트워크가 끊겨도 마지막 정상 카탈로그로 추천을 계산할 수 있다.
- 카탈로그 갱신이 개인 데이터와 과거 결제 snapshot을 변경하지 않는다.
- 로그인해도 기존 로컬 데이터는 그대로 유지되며 명시적으로 빈 계정에 백업할 수 있다.
- 다른 빈 기기에서 로그인하면 계정 snapshot을 명시적으로 내려받아 검증 후 복원할 수 있다.
- 계정과 기기에 서로 다른 데이터가 있으면 자동 덮어쓰기나 병합 없이 충돌 상태로 차단된다.

### 정확성

- 같은 입력과 catalog 버전에서 서버 기준 fixture와 브라우저 결과가 일치한다.
- 일·월·연 한도와 이전 실적/결제 사용량이 동일하게 반영된다.
- 만료, 일시 정지, 조건부, 정보 전용 프로모션의 처리가 기존 정책과 일치한다.
- 과거 결제 내역은 최신 카탈로그가 아니라 저장 당시 snapshot을 표시한다.

### 성능과 복원력

- 카탈로그가 캐시된 뒤 추천 계산에는 네트워크 왕복이 없다.
- 목표 모바일 기기에서 입력 UI가 계산 때문에 눈에 띄게 멈추지 않는다.
- 카탈로그 다운로드 실패, IndexedDB quota 오류, sync 재시도와 충돌을 복구할 수 있다.
- 전체 snapshot과 개인 export를 테스트 환경에서 복원할 수 있다.

## 13. 아직 결정할 사항

- 소액 혜택 기준을 할인액만으로 볼지, 포인트·캐시백·편의 비용까지 환산한 순혜택으로 볼지
- 기본 임계값을 100원 미만으로 둘지, `100원 이하`로 둘지와 사용자별 임계값 조정 허용 여부
- 임계값 미만일 때 혜택 추천을 완전히 제외할지, 낮은 우선순위로 남기고 실적 우선 결제를 함께 제시할지
- 실적 우선 추천에서 다음 달 실적을 위해 사용할 카드의 월 목표액·남은 금액·제외 항목을 어떻게 보여줄지
- 첫 sync 버전에서 모든 개인 데이터를 동기화할지, 프로필·실적·기록부터 시작할지
- IndexedDB wrapper를 직접 구현할지 검증된 경량 라이브러리를 사용할지
- sync 서버가 레코드 단위 변경 로그를 처음부터 가질지, 초기에는 workspace snapshot 동기화로 시작할지
- 민감한 개인 데이터에 종단간 암호화 백업을 제공할지
- 여러 계정이 같은 브라우저를 사용할 때 local workspace를 어떻게 분리할지
- 관리자 인증을 현재 이메일/비밀번호 방식으로 유지할지 별도 접근 제어와 결합할지
- 카탈로그를 private ingress 안에서만 제공할지 향후 공개 캐시/CDN으로 제공할지
- 계산 후보 수 상한과 성능 목표를 어떤 실제 휴대폰을 기준으로 정할지
- AI 구조화에 사용할 모델·JSON schema·호출 예산과 문서별 재시도 정책
- AI가 낮은 신뢰도로 추출한 카드 규칙을 자동 게시할 수 있는 조건과 필수 수동 검수 기준
- 원문 문서와 AI extraction 결과를 SQLite에 저장할지 별도 object storage에 저장할지
- 카드 상품의 지원 범위를 발급량·사용자 수요·문서 품질 중 어떤 우선순위로 확장할지

## 14. 다음 세션의 권장 첫 작업

비로그인 경로, 명시적 snapshot 병합, 선택 계정의 자동 증분 동기화와 계정 수명주기 데이터 선택까지 동작한다. 다음 안전 작업은 실제 기기 성능을 확인하고 추천 정책 고도화를 시작하는 것이다.

1. 실제 휴대폰에서 카탈로그 다운로드·추천 계산·IndexedDB 복원 시간을 측정한다.
2. 카드별 월 실적 목표와 다음 달 전환 시점을 반영한 실적 우선 추천을 구현한다.
3. 소액 혜택 임계값과 `이번 결제 혜택`·`다음 달 실적 대비` 추천 사유를 구현한다.
4. 대표 카드 1~2개를 대상으로 원문 수집 → AI 구조화 → 스키마 검증 → 검수 → 규칙 fixture 검증의 수직 흐름을 만든다.
5. AI extraction 결과와 게시된 benefit rule의 revision·근거·rollback 데이터 모델을 확정한다.

자동 동기화는 IndexedDB schema v2의 `sync-state`와 `sync-outbox`를 사용한다. 로컬 변경은 device ID, base revision과 UUID operation ID를 가진 outbox snapshot으로 원자 저장된다. 서버는 `account_workspace_operations`에서 계정별 operation ID와 요청 hash를 기록해 재전송을 한 번만 반영하며, stale base revision은 기존 레코드 metadata의 `updatedAt`과 tombstone 우선순위로 병합한다. pull은 revision cursor 이후 변경이 있을 때만 최신 검증 snapshot을 반환한다. 실패한 outbox는 5초부터 최대 1시간까지 backoff하고, 온라인 복귀·화면 재진입·30초 주기·수동 실행에서 다시 시도한다.

일회성 account import는 첫 안전 경로로 snapshot 방식을 사용한다. 서버는 공용 카탈로그를 제외한 계정 개인 데이터만 owner 없는 transport로 내리고, 브라우저가 기존 로컬 workspace ID와 기기 ID를 유지한 채 소유권을 다시 연결한다. 로컬 workspace에 변경이나 tombstone이 하나라도 있으면 import를 중단하므로 반복 실행으로 레코드가 중복되거나 기존 기기 데이터가 사라지지 않는다.

기존 서버 사용자 레코드와 인증 경로는 snapshot 전환과 롤백이 검증될 때까지 유지한다. 현재 로그인은 데이터 모드를 전환하지 않으며, 설정의 계정 연동 화면에서만 백업·복원 mutation을 수행한다.
