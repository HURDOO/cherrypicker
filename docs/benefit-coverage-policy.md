# 혜택 반영 단계와 미지원 규칙·브랜드 대응 정책

- 상태: 승인 — 2026-10-10 사용자 결정. 구현은 `TASK-10`에서 진행한다.
- 적용 대상: 카드 혜택 후보, 프로모션이 발견한 브랜드, 카드 후보가 참조하는 결제처
- 관련 문서: [`card-benefit-source-policy.md`](./card-benefit-source-policy.md), [`card-benefit-dsl-v1.md`](./card-benefit-dsl-v1.md), [`promotion-source-policy.md`](./promotion-source-policy.md)

## 1. 원칙

카드가 늘수록 앱이 아직 계산하지 못하는 규칙과 등록되지 않은 결제처가 계속 등장한다. 모든 문구를 계산할 수 있을 때까지 카드 전체를 막지 않고, **과대 계산만 막는다.** 혜택을 덜 보여주는 쪽의 오차는 안내 문구로 보완하고, 실제보다 많이 보여주거나 추천 순위를 부풀리는 오차만 차단한다.

## 2. 반영 단계

| 단계 | 기준 | 사용자 표시 |
| --- | --- | --- |
| 자동 계산 | 금액·조건·한도를 결제금액·결제처·채널·시각·실적·이용 기록 등 현재 입력만으로 판정한다. | `확정` |
| 조건 확인 | 앱은 알 수 없지만 결제 순간 사용자가 예/아니오로 답할 수 있다. 지정 판매처, 행사 상품, 승인 업종·PG 제외, 자동이체 여부가 해당한다. | `조건 충족 시` |
| 정보 제공 | 원화 금액으로 바꿀 수 없거나 일상 결제 추천과 관계가 낮다. | 0원과 공식 조건 문구 |
| 카드 주의 문구 | 개별 혜택이 아니라 카드 전체에 걸리는 조건이며 앱이 판정할 수 없다. | 카드·실적 안내의 한 줄 문구 |
| 게시 차단 | 위 단계로 내려도 과대 계산을 막을 수 없다. | 해당 규칙 미게시 |

### 정보 제공으로 고정하는 항목

1. 외부 변수에 따라 금액이 정해지는 혜택: 주유 리터당 할인·적립, 환율, 해외 이용·ATM 수수료
2. 현금이 아닌 혜택: 공항 라운지, 무료 제공, 보험, 쿠폰·사은품, 마일리지
3. 금융상품 혜택: 우대금리, 수수료 면제
4. 응모·추첨·선착순 행사
5. 한 문구에 요율이 여럿이고 현재 사용자 프로필로 하나를 정할 수 없는 혜택
6. 연 1~2회 수준의 저빈도 혜택: 테마파크 연간 횟수, 생일 혜택 등

특정 상품 할인(편의점 행사상품 등)은 기존처럼 `조건 충족 시`로 표시하고, 사용자가 대상 상품 금액을 입력하면 계산한다.

## 3. 규칙 단위 게시

- 금액·조건·한도에 영향을 주는 미지원 문구는 연결된 `ruleIds`의 규칙만 낮춘다. 같은 카드의 나머지 규칙은 검증을 통과하면 게시한다.
- 낮추는 순서는 `조건 확인` → `정보 제공` → `게시 차단`이다. 사용자 질문 하나로 과대 계산을 막을 수 있으면 조건 확인, 그렇지 않으면 0원 정보 제공으로 둔다.
- 낮춘 규칙이 다른 규칙과 한도를 공유하는 등 정보 제공으로도 다른 계산을 부풀릴 수 있으면 해당 규칙과 공유 그룹만 게시에서 제외하고 카드 지원 범위에 `미반영 혜택`으로 표시한다.
- 카드 통합 한도처럼 카드의 모든 계산 규칙을 제한하는 문구를 표현할 수 없으면 모든 계산 규칙이 영향을 받으므로 카드 게시를 보류한다.
- 낮춘 규칙과 미게시 규칙은 확정 총액과 기본 추천 순위에 포함하지 않는다.

### 카드 실적 제외

공식 실적 제외 중 앱이 거래 종류를 판정할 수 없는 항목(무이자할부, 상품권, 세금 등)은 게시를 막지 않고 카드 주의 문구로 안내한다. 예상 실적은 기존처럼 승인금액 기준으로 반영하고 판정 가능한 제외만 적용한다. 사용자는 기존 수동 실적 보정으로 바로잡을 수 있다. 결제 기록 단계에 거래 종류 입력을 추가하지 않는다.

## 4. 미지원 패턴

- 미지원 문구는 자유 텍스트만이 아니라 등록된 **패턴 ID**를 가진다(예: `PERF_EXCLUDE_INSTALLMENT`, `PG_EXCLUDED`).
- 패턴은 의미, 반영 단계, 사용자 문구와 일상 카테고리 여부를 정의한다. 같은 패턴은 모든 카드에서 같은 단계와 문구로 처리한다.
- AI 후보는 등록된 패턴을 선택하거나 새 패턴을 제안한다. 새 패턴은 검수에서 등록하기 전까지 해당 규칙을 게시하지 않는다.
- 카드별 정규식 검증을 새로 추가하지 않는다. 기존 카드 전용 검증은 패턴 또는 범용 검증으로 옮긴다.

### 엔진 확장 검토 기준

- 일상 카테고리 결제처에 걸린 패턴은 게시 카드 1장에서 나와도 DSL 확장을 검토한다. 일상 카테고리는 `PROJECT_BRIEF.md` §8의 편의점·카페·마트·다이소·올리브영·교통·통신·온라인 쇼핑과 외식·배달이다.
- 그 밖의 패턴은 같은 패턴 ID가 게시 카드 3장 이상에서 나올 때 검토한다.
- 검토 전까지는 위 반영 단계로 처리한다. 확장은 범용 입력·연산자로만 하며 카드 ID 분기를 만들지 않는다.

## 5. 브랜드

| 대상 | 처리 |
| --- | --- |
| 식별 가능한 실제 매장·온라인몰 | 카드 후보가 이름·카테고리·별칭·공식 인용과 함께 새 브랜드를 제안한다. 기존 브랜드와 별칭 매칭으로 중복을 먼저 확인하고, 혜택 승인 트랜잭션에서 브랜드와 규칙을 함께 등록한다. 미승인 후보의 브랜드는 공개 카탈로그에 넣지 않는다. |
| 경기·상품·장소 등 매장이 아닌 범위 | 기존처럼 근거 있는 `purchaseScenario`로 표현한다. |
| 열거할 수 없는 판매처 집합 | 카테고리와 확인 질문으로 `조건 충족 시` 처리하며 카테고리 전체 확정 혜택으로 넓히지 않는다. |

### 검색 전용 노출

새로 추가되는 브랜드는 카드·프로모션 출처와 관계없이 **검색 전용**을 기본으로 한다.

- 숨김: 카테고리 목록, 전체 목록, 기본 인기 목록
- 노출: 이름·별칭·초성 검색, 즐겨찾기, 최근·자주 이용, 개인 혜택 제안
- 사용자가 즐겨찾기하거나 이용하면 해당 사용자의 개인 목록에서 기존 순위 규칙대로 올라온다.
- 기존 브랜드의 노출은 바로 바꾸지 않는다. 프로모션이 자동 생성한 기존 브랜드를 포함한 재분류 목록을 만들어 사용자 확인 후 적용한다.

## 6. 현재 구현과의 차이

2026-10-10 기준 아래는 아직 구현되지 않았다.

- 승인 검증은 `affectsValue=true` 미지원 문구가 하나라도 있으면 카드 후보 전체를 차단한다.
- 미지원 문구에 패턴 ID가 없다.
- 카드 결제처는 관리자 사전 등록(`/api/admin/system-brands` create-only)으로만 추가한다.
- 브랜드 노출 속성이 없어 모든 브랜드가 탐색 목록에 나온다. 프로모션은 발견한 브랜드를 자동 생성한다.
- `src/lib/card-benefit-extraction.ts`에 카드 원문 전용 정규식 검증이 남아 있다.
- 판정할 수 없는 실적 제외는 카드 주의 문구가 아니라 금액 영향 미지원 문구로 게시를 차단한다.
