# Cherrypicker 제품 명세

## 1. 상태

- 상태: 비공개 실사용 베타 준비
- 기준일: 2026-09-04
- 입력: `PROJECT_BRIEF.md`와 2026-09-04 사용자 승인
- 현재 구현: 로그인 없는 첫 설정·추천·기록, 로컬 workspace, 선택적 계정 동기화, 공용 카탈로그, 관리자 수집·검수·revision·rollback 기반은 존재한다.
- 남은 범위: 일반 결제처 추천, 신뢰성 회귀 검증, 베타 카드 범위, 실기기 검증과 운영 준비는 `docs/TASKS.md`에서 관리한다.

## 2. 목표와 해결할 문제

Cherrypicker는 사용자가 결제처와 금액을 입력하면, 이미 보유한 카드·통신사 멤버십·구독·페이·포인트를 함께 비교해 이번 결제의 가장 유리한 조합과 이유를 알려준다. 새 카드 발급 유도보다 보유 수단의 실사용 가치를 높이는 것이 우선이다.

해결할 문제는 다음과 같다.

- 공식 혜택 정보가 여러 제공자에 흩어져 있고 조건과 한도가 복잡하다.
- 결제 직전에 모든 보유 수단을 수동으로 비교하기 어렵다.
- 소액 할인·적립과 카드 실적 가치는 누적하면 의미가 있지만 놓치기 쉽다.
- 혜택이 변경·종료되어도 사용자가 매번 공식 문서를 다시 확인하기 어렵다.

## 3. 주요 사용자

- 카드 2장 이상을 보유하고 결제처에 따라 카드를 바꿔 쓰는 사람
- 통신사 멤버십, 간편결제, 포인트와 구독 혜택을 함께 사용하는 사람
- 작은 할인·적립도 꾸준히 챙기는 청년층과 앱테크 사용자
- 초기 검증은 프로젝트 소유자와 주로 20대 대학생인 지인 3~4명을 대상으로 한다.

## 4. 핵심 사용 흐름

### 4.1 첫 사용

1. 로그인하지 않고 앱을 열어 짧은 서비스 소개와 로컬 개인정보 안내를 확인한다.
2. 다음을 눌러 보유 카드를 검색해 선택한다.
3. 원하면 멤버십·구독·페이·포인트, 실적과 즐겨찾기를 설정한다. 즐겨찾기는 소수의 인기 브랜드가 기본 선택되며 인기순·생활 카테고리·검색으로 고치기 쉬워야 한다.
4. 실적을 모르거나 귀찮은 사용자는 카드 선택만으로 다음 단계로 갈 수 있다.
5. 튜토리얼의 `브랜드 선택 → 금액 입력 → 혜택 확인` 안내를 따라 첫 추천을 확인한다. 선택한 멤버십·구독·페이와 카드의 현재 실적·남은 한도를 함께 계산해 확정 혜택을 받을 수 있는 브랜드와 예시 결제 금액을 먼저 제안한다.

첫 설정은 별도 설명서 없이 2~3분 안에 완주할 수 있어야 한다. 소개·카드·혜택·실적·즐겨찾기·첫 추천은 구분된 URL을 사용하고 브라우저 뒤로가기와 히스토리에서 자연스럽게 이동해야 한다. 은행 앱을 확인하고 돌아오거나 새로고침해도 작성 중인 설정을 불필요하게 잃지 않는다.

### 4.2 반복 사용

1. 즐겨찾기 또는 검색에서 결제처를 고른다.
2. 금액을 입력한다.
3. 가장 유리한 조합, 이번 결제의 혜택과 추천 이유를 확인한다.
4. 필요하면 `조건 충족 시` 조건을 확인한다.
5. 실제로 사용한 조합을 기록한다.
6. 갱신된 실적, 혜택 한도와 누적 혜택을 확인한다.

재방문 사용자는 앱 열기부터 추천 확인까지 약 10초 안에 끝낼 수 있어야 한다.

### 4.3 브랜드·카드 미지원

- 브랜드가 없으면 `일반 결제 추천`으로 특정 브랜드 전용 혜택을 제외한 조합을 받는다.
- 카드가 없으면 미지원 상태를 알 수 있어야 하며, 비공개 베타에서는 소유자에게 카카오톡으로 추가 요청을 보낸다.
- 필요하면 커스텀 카드·규칙을 사용할 수 있지만 공식 시스템 카드와 혼동하지 않는다.

## 5. 기능 요구사항

### 5.1 비로그인·로컬 사용

- FR-001: 홈, 설정과 결제 기록은 로그인 없이 작동해야 한다.
- FR-002: 개인 카드·실적·혜택 프로필·결제 기록은 기본적으로 현재 브라우저 origin의 IndexedDB에 저장해야 한다.
- FR-003: 사용자는 개인 workspace를 JSON으로 내보내고 다시 가져올 수 있어야 한다.
- FR-004: 로그인은 사용 관문이 아니며 계정 백업·복원·동기화를 위한 선택 기능이어야 한다.
- FR-005: 로그인·복원·병합 과정에서 로컬 또는 계정 데이터를 조용히 덮어쓰거나 삭제하지 않아야 한다.

### 5.2 설정과 탐색

- FR-006: 신규 사용자는 간단한 서비스 소개 뒤 안내된 순서로 카드, 혜택 프로필, 실적과 즐겨찾기를 설정할 수 있어야 한다. 각 단계는 고유 URL과 전환 효과를 사용해 뒤로가기·새로고침·재개가 가능해야 한다. 새 즐겨찾기는 여러 생활 영역의 인기 브랜드 일부를 기본 선택하고 인기순·카테고리·검색 탐색을 제공해야 한다.
- FR-007: 카드 선택 외의 초기 항목은 건너뛸 가능해야 하며, 나중에 설정에서 보완할 수 있어야 한다. 첫 소개 화면부터 실적 등 개인 정보를 입력하는 화면까지 해당 값이 현재 브라우저에 저장되고 추천도 기기에서 계산되며, 사용자가 계정 백업·동기화를 직접 켜기 전에는 서버로 전송되지 않는다는 점을 가까이 안내해야 한다. 통신사 멤버십을 고르면 등급도 함께 입력해 등급별 제휴 혜택이 누락되거나 과대 계산되지 않게 한다. 설정 직후 첫 추천은 브랜드 선택·금액 입력·결과 확인을 단계별로 크게 안내하고, 멤버십·구독·페이·카드 실적·남은 한도·오늘 조건을 합친 확정 혜택 브랜드와 예시 결제 금액을 우선 제안해야 한다.
- FR-008: 사용자는 브랜드를 즐겨찾기, 최근 기록, 카테고리, 이름·별칭·초성 검색으로 찾을 수 있어야 한다.
- FR-009: 자주 쓰는 일상 브랜드를 빠른 선택에 우선 노출하고, 저빈도 브랜드는 기타·검색으로 찾을 수 있게 한다.
- FR-010: 검색 결과가 없을 때 재검색과 일반 결제 추천을 명확히 제공해야 한다.

### 5.3 추천과 표현

- FR-011: 추천은 통신사·매장 할인, 페이, 카드·머니·포인트 결제수단, 결제 후 적립을 결합해 비교해야 한다.
- FR-012: 큰 금액은 이번 결제에서 얻는 혜택만 표시하고 실적 증가액을 혜택처럼 표시하지 않는다.
- FR-013: 혜택을 `확정`, `조건 충족 시`, `정보 제공`으로 구분하고 확정 혜택을 기본 순위 기준으로 삼는다.
- FR-014: 자동이체, 특정 상품, 승인 가맹점·결제 채널 등 앱이 알 수 없는 조건을 숨기지 않고 사용자가 확인하게 한다.
- FR-015: 계산할 수 없는 혜택을 최대 금액으로 임의 환산해 추천 순위에 넣지 않는다.
- FR-016: 확정 즉시 혜택이 없거나 사용자의 소액 기준보다 작으면 다음 달 실적 관점의 추천을 제공할 수 있다.
- FR-017: 소액 기준은 기본 100원이며 설정에서 변경할 수 있어야 한다.
- FR-018: 추천 이유는 계산식 전체보다 사용자가 결제 수단을 고를 수 있는 짧은 문장으로 제공한다.

### 5.4 결제 기록과 후속 상태

- FR-019: 사용자는 실제로 사용한 추천 조합을 한 번의 명확한 확정 행동으로 기록해야 한다.
- FR-020: 기록은 결제 시점의 조합·규칙·카탈로그 버전 snapshot을 보존해야 한다.
- FR-021: 기록한 결제는 해당 카드의 현재 실적과 일·월·연 혜택 사용량에 반영되어 다음 추천을 바꿔야 한다.
- FR-022: 히스토리에서 기록과 확인된 누적 혜택을 다시 볼 수 있어야 한다.

### 5.5 공용 혜택 카탈로그

- FR-023: 공용 카탈로그는 게시된 시스템 카드·규칙·브랜드·프로모션·제공자·승인 경로와 공개 지원 정보만 포함해야 한다.
- FR-024: 브라우저는 마지막 정상 카탈로그를 저장하고, 갱신 실패·오프라인에서도 저장본으로 추천과 기록을 계속할 수 있어야 한다.
- FR-025: 관리자 수집 실패, 검증 실패나 미승인 후보가 현재 게시본을 제거하지 않아야 한다.

### 5.6 수집·검수·관리

- FR-026: 관리자는 공식 출처 등록, 원문 수집, 구조화 후보, 필드별 근거, diff와 검증 오류를 확인할 수 있어야 한다.
- FR-027: 삭제·조건 제거·한도 증가 등 고위험 변경은 명시적 검수 없이 게시하지 않는다.
- FR-028: 승인된 카드 혜택은 revision으로 보존하고 이전 정상 revision으로 rollback할 수 있어야 한다.
- FR-029: 관리자는 수집 실행, 카드별 상태, AI 호출·캐시, 검증 실패와 연속 문제를 확인할 수 있어야 한다.
- FR-030: AI는 공개 공식 문서의 후보 생성만 돕고 자체 게시 권한을 갖지 않는다.

## 6. 비기능 요구사항

### 6.1 성능과 복원력

- NFR-001: 초기 카탈로그를 정상 수신한 뒤 추천 계산은 네트워크 요청 없이 기기에서 수행해야 한다.
- NFR-002: 모바일 실기기에서 첫 추천은 2~3분 안에, 재방문 추천은 앱 열기부터 약 10초 안에 확인 가능해야 한다.
- NFR-003: 카탈로그·수집 갱신 실패는 마지막 정상 게시본과 브라우저 저장본을 훼손하지 않아야 한다.

### 6.2 보안과 개인정보

- NFR-004: 비밀값, SQLite·WAL, 백업과 개인 export를 Git이나 공개 카탈로그에 포함하지 않는다.
- NFR-005: 관리자 화면·API는 세션과 관리자 권한을 모두 검증해야 하며, 쓰기 API는 same-origin 검증을 유지해야 한다.
- NFR-006: 서버 API는 클라이언트가 보낸 user ID를 소유권의 근거로 신뢰하지 않는다.
- NFR-007: AI에 개인 카드, 실적, 결제 기록과 계정 데이터를 보내지 않는다.
- NFR-008: 공개 회원가입은 필요한 계정을 만드는 기간에만 명시적으로 열고 평소에는 닫는다.

### 6.3 접근성과 호환성

- NFR-009: 핵심 입력, 탭, 조건 확인과 기록 버튼은 키보드로 조작할 수 있고 의미 있는 레이블·상태를 제공해야 한다.
- NFR-010: 모바일을 우선하되 지원하는 데스크톱 브라우저에서도 핵심 흐름을 완주할 수 있어야 한다.
- NFR-011: IndexedDB를 사용할 수 없는 환경, 오프라인, 저장 실패와 오래된 카탈로그를 서로 다른 상태로 안내해야 한다.
- NFR-012: 카카오톡 내 브라우저, Chrome과 Safari가 서로 다른 로컬 데이터를 갖을 수 있다는 점을 브라우저 origin 용어 없이 쉽게 설명해야 한다.

### 6.4 운영

- NFR-013: 카드 원문은 주 1회, 페이·통신사 등 프로모션은 매일 새벽·아침에 단일 외부 스케줄러로 확인하는 것을 목표로 한다.
- NFR-014: 원문 의미 hash가 같으면 AI 구조화 결과를 재사용하고, 변경 카드만 설정된 호출 상한 안에서 다시 처리한다.
- NFR-015: 비공개 베타 전까지는 남은 OpenAI credit 범위에서 개발하며 추가 비용은 사용자 승인 없이 발생시키지 않는다.
- NFR-016: 비공개 베타에서 행동 테레메트리를 수집하지 않고 소유자가 직접 피드백을 받는다.

## 7. 데이터 요구사항

- 공용 카탈로그: 시스템 카드·혜택 규칙·브랜드·카테고리·게시 프로모션·제공자·승인 경로·검수 상태·version과 freshness를 포함한다.
- 로컬 workspace: workspace·device ID, 커스텀 항목, 보유 시스템 카드 상태, 실적, 혜택 프로필, 결제 기록, tombstone과 항목별 수정 시각을 포함한다.
- 추천 기록: 원 결제액, 결제처, 선택 조합, 확정·조건부·예상 가치, 실적 기여액과 카탈로그 버전이 포함된 snapshot을 보존한다.
- 수집 데이터: 공식 URL, 원문·PDF bytes, extracted text, 수집 시각, content·bundle hash, 문서 version, 후보, 필드별 근거, audit, diff, 검수자, revision과 실행 결과를 보존한다.
- 계정 workspace: 사용자별 snapshot, content hash, 단조 증가 revision과 멱등 operation을 서버에 보존한다.
- 사용자 자료 삭제는 개인 workspace·계정 삭제와 공용 카탈로그 삭제를 구분해야 한다.

## 8. 외부 연동

- 카드사·통신사·결제사·브랜드의 공개 공식 HTML·JSON·PDF: 수집·근거의 우선 출처
- OpenAI Responses API: 공개 카드 혜택 문서의 인벤토리와 구조화 후보 생성
- Better Auth: 선택적 계정과 관리자 세션
- deployd·GHCR: Raspberry Pi 관리형 이미지 배포와 상태 확인
- Discord webhook: 운영 장애 알림을 구현할 때 연결하며 URL은 구현 직전에 사용자에게 받는다.

로그인, CAPTCHA, 접근 제한을 우회하는 수집은 하지 않는다. MyData·금융기관·카드사 계정 연동은 현재 범위에 포함하지 않는다.

## 9. 범위 제외

- 모든 국내 카드의 완전한 지원
- 카드사 로그인·앱 내부 scraping을 통한 거래 자동 수집
- MyData 또는 금융기관 계약이 필요한 자동 거래 연동
- 네이티브 모바일 앱과 모바일 백그라운드 항상 실행 추천
- 모든 라운지·보험·마일리지·유가 혜택의 원화 정밀 계산
- AI가 고위험 변경을 사람 검수 없이 게시하는 기능
- 비공개 베타 기간의 행동 테레메트리, 앱 내 제보 폼, 공식 Discord·Google Form
- 비공개 베타 기간의 공개 사용자용 개인정보 처리방침·SNS 홍보

## 10. 완료 조건

다음을 모두 관찰·검증하면 비공개 실사용 베타 준비가 끝난다.

- 새 브라우저에서 로그인 없이 카드를 선택하고 나머지 설정을 건너뛰 2~3분 안에 첫 추천과 기록을 완주한다.
- 재방문 사용자가 실기기에서 즐겨찾기·검색→금액→추천을 약 10초 안에 완주한다.
- 미지원 브랜드에서 일반 결제 추천을 받으며 특정 브랜드 혜택이 잘못 포함되지 않는다.
- 확정·조건부·정보 제공과 실적 우선 이유가 구분되고, 자동 계산 혜택의 대표 경계 시나리오에서 과대 계산이 없다.
- 기록 후 실적·일·월·연 한도가 다음 추천에 반영되고 과거 기록은 당시 snapshot을 유지한다.
- 베타 참여자가 보유한 핵심 카드가 공식 검수 게시 또는 명확한 미지원 상태로 분류된다.
- 새로 수집한 후보·실패·삭제 의심이 현재 게시본을 훼손하지 않고 관리자만 승인·rollback할 수 있다.
- 수집 일정과 실패 상태를 확인할 수 있고, 운영 DB의 기존 백업·복구 절차를 한 번 검증한다.
- `npm run lint`, `npm test`, `npm run build`가 통과하고 배포 후 핵심 공개·관리자 경계를 smoke test한다.

## 11. 명시된 요구사항

- 첫 베타는 주로 20대 대학생 지인 3~4명으로 시작한다.
- 실적 입력은 선택이며 카드 선택만으로 시작할 수 있어야 한다.
- 베타 참여자의 보유 카드를 시작 전에 직접 묻고 지원 순서에 반영한다.
- 일반 결제처 추천을 제공한다.
- 비공개 베타의 오류·카드 요청은 소유자가 카카오톡으로 직접 받고 행동 테레메트리는 수집하지 않는다.
- 카드는 주 1회, 프로모션은 매일 새벽·아침에 수집한다.
- 추가 AI 비용, 운영 secret, 공개 배포, 삭제·마이그레이션은 별도 승인 범위로 다룬다.

## 12. 추론한 가정

- 브리프의 `베타때까지 백업 예정 없음`은 새 상시 외부 복제·보존 체계를 추가하지 않는다는 뜻으로 해석한다. 이미 구현된 배포 전 snapshot과 백업 검증·복구 절차는 유지하고 베타 전 1회 확인한다.
- `약 10초`는 서버 성능 번치마크만이 아니라 사용자가 앱을 열고 브랜드·금액을 선택해 추천을 읽는 실제 완주 시간을 뜻한다.
- 비공개 베타의 `제보를 남길 수 있음`은 앱 내 제보 시스템이 아니라 소유자와의 직접 카카오톡 연락으로 충족한다.
- 베타 성공 판단은 고정 기간·자동 지표가 아니라 소수 참여자의 반복 사용과 정성 피드백에 대한 소유자의 판단으로 한다.

## 13. 결정이 필요한 사항

다음은 현재 문서 작성을 막지 않지만 해당 작업 직전에 확정해야 한다.

- 베타 참여자 3~4명의 실제 보유 카드 목록과 우선 결제 상황
- 장애 알림 구현 시 사용할 Discord webhook URL과 메시지 수신 범위
- 현재 credit을 초과하는 OpenAI 추가 비용 지출 여부
- 오픈 베타 전 개인정보·이용 안내, 공식 피드백 채널, 선택적 지표와 외부 백업 보존 정책
