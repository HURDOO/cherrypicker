## 2026-10-19: 카카오페이 굿딜 할인율을 데모 전에 정보 표시로 연동

- 상태: 승인 — 사용자가 1주 관측 결과와 정보 표시 방식 제안을 보고 데모 전 연동을 골랐다. 데모 전까지는 할인율만 기록하기로 했다. 정책 문서의 예외 문안, 기록 가져오기 방식, 관측 주기는 TASK-16에서 확정한다.
- 맥락: 2026-10-11~10-19에 14회 관측했고 모두 성공했다. 할인율은 두 번 바뀌었고, 두 번 모두 월요일이 낀 구간이었다. 108개 중 9개 브랜드가 바뀌었다. 2026-10-12 화면 변경 뒤로 `혜택` 표시는 접근성 트리에 없어서 할인율만 읽을 수 있다. 하루 한도와 기간은 바코드와 함께 그려지는 브랜드 상세 화면에만 있다. 사용자는 1주 동안 카카오페이의 경고나 기능 제한을 보지 못했다.
- 결정:
  - 사용자가 폰 관측 앱으로 굿딜 홈을 직접 관측한 기록을 `promotion-source-policy.md`의 앱 내부 수집 제외에 대한 예외로 둔다. 서버의 자동 수집이 아니라 사용자의 수동 관측이다. 개인화 영역(`<이름>님을 위한 추천`, `최근 결제`)은 폰에서 버리고 가져오지 않는다.
  - 할인율은 확정 총액에 넣지 않는 정보 혜택으로 결제처 추천에 보여 주고, 관측 날짜를 함께 표시한다. 한도와 기간을 모른 채 금액을 계산하면 과대 계산이 되기 때문이다.
  - 가져온 기록은 로컬에서 검수하고, 승인본만 운영으로 옮긴다(2026-10-12 결정).
  - 행사 여부와 기간은 데모 후에 브랜드 상세 화면까지 들어가 가져오는 방향을 검토한다. 상세 화면은 바코드와 함께 그려지므로, 진입 방식과 안전 조건은 그때 따로 정한다.
- 고려한 대안: 데모 후 연동, 연동하지 않고 관측 종료, `혜택` 표시를 10% 이상으로 추정해 기록
- 결과와 트레이드오프: 데모 참여자에게 굿딜 할인율을 보여 줄 수 있다. 한계도 있다.
  - 한 계정의 관측이라 다른 사용자도 같은 율을 받는지 모른다.
  - 사람이 버튼을 눌러야 관측되므로, 주기를 놓치면 오래된 값이 보인다. 관측 날짜 표시가 이를 알리는 유일한 장치다.
  - 화면 구조가 바뀌면 관측 앱을 고쳐 USB로 다시 설치해야 한다.
- 근거: [카카오페이 굿딜 관측 경로 검증](./kakaopay-gooddeal-observation.md)

## 2026-10-12: 데모 전 카드 범위를 인기 체크카드 66장으로 고정

- 상태: 승인 — 사용자가 체크카드 한정, 7개 카드사, TOP100 전체와 7개사 밖 상위권 4장 추가를 정했다.
- 맥락: 데모 참여자의 보유 카드를 미리 물어볼 수 없고, 사용자는 데모 때 카드 목록이 변수가 되면 안 된다고 했다. 참여자는 대학생이라 체크카드 비중이 높다. 브리프 §8은 전체 카드 시장을 한 번에 수집하지 않고 지원 카드가 맞는 사용자부터 초대한다고 했으며, 2026-09-07 결정은 참여자 카드를 시작 직전에 추가하기로 했다.
- 결정: 2026-10-12 주간 체크카드 인기 TOP100 중 신한·KB국민·현대·우리·하나·NH농협·카카오뱅크 카드와 케이뱅크 ONE·네이버페이 머니카드·토스뱅크 체크·토스뱅크 K-패스를 데모 전에 게시한다. 하이패스·개인사업자·청소년·국비 바우처 전용 카드는 제외한다. 신규 58장, 디자인·은행 변형 8장이다. 순위는 대상 선정에만 쓰고 계산 근거는 카드사 공식 원문만 쓴다. 이 범위 밖 카드는 데모 중 요청을 받아 기존 동적 추가 절차로 처리한다. 2026-09-07의 참여자 카드 직전 추가 결정은 이 범위 밖 카드에만 적용된다.
- 고려한 대안: 카드사별 인기 상위 약 25장만 먼저, 참여자 보유 카드 사전 조사, 7개사 전체 체크카드(약 237장)
- 결과와 트레이드오프: 데모 참여자가 흔한 체크카드를 고르면 바로 지원된다. 카드 수만큼 세션 구조화 작업과 원문 변경 시 수정안 부담이 늘고, 순위 밖 카드나 신용카드는 여전히 빠질 수 있다. 진행은 [체크카드 TOP100 수집 현황](./check-card-top100-2026-10.md)에서 관리한다.

## 2026-10-12: TASK-14 카드는 검증을 통과하면 세션이 로컬 DB에서 임시 승인

- 상태: 승인(임시) — 사용자가 사람 개입을 줄이기 위해 임시 승인 방식을 정했다.
- 맥락: 66장을 세션이 사용자 부재 중에 처리하고, 사용자는 판단이 필요한 항목만 모아서 정하려 한다. 브리프 §9는 AI가 게시 권한을 갖지 않는다고 했다. 작업은 로컬 DB에서만 하고 운영 반영은 TASK-06의 별도 관문을 거친다.
- 결정: TASK-14 대상 카드에 한해 validation·audit 오류와 근거 누락이 0건이고, 계산을 과대하게 만들 수 있는 결정 대기 항목이 없고, golden fixture와 전체 테스트가 통과하면 세션이 `cards:revise --approve`로 로컬 DB에서 승인한다. 선택형 혜택을 확인 질문으로 둘지처럼 사용 편의만 바꾸는 결정은 보수적인 형태로 승인하고 결정 대기 목록에 남긴다(2026-10-12 시범 카드에서 보완). 수정안 메모는 `[세션 임시 승인]`으로 시작해 사람 승인과 구분한다. 하나라도 어긋나면 검수 대기로 두고 결정 대기 목록에 사유를 남긴다. 임시 승인 카드는 운영 반영 전에 사용자가 확인한다.
- 고려한 대안: 세션은 검수 대기까지만 만들고 사용자가 모두 승인
- 결과와 트레이드오프: 사용자가 돌아왔을 때 정할 항목만 남는다. 검증기가 잡지 못하는 의미 오류가 로컬 카탈로그에 들어갈 수 있으므로, 운영 반영 전 사용자 확인과 TASK-06의 반영 관문이 최종 보호 장치다. TASK-14가 끝나면 이 위임을 유지할지 다시 정한다.

## 2026-10-12: 카탈로그는 로컬에서 검수하고 운영으로 옮긴다

- 상태: 제안 — 사용자가 방향에 동의했다. 옮기는 통로의 구체 구현은 TASK-06 시작 전에 사용자와 상의해 정한다.
- 맥락: 카드 수정안 도구(`cards:revise`)는 사람이 연 세션에서 로컬 DB에 대해 실행된다. 운영 앱은 2026-09-17 이미지와 seed 카드 8장인 빈 DB로 시작했고, 로컬 검수 카드·프로모션은 운영에 반영된 적이 없다. 카탈로그를 내보내고 가져오는 기능은 아직 없다.
- 결정: 카드 revision과 프로모션은 로컬에서 수집·검수·승인하고, 승인된 카탈로그만 운영으로 옮긴다. 로컬 DB 전체를 운영에 덮어쓰지 않는다(테스트 계정·workspace·세션이 섞여 있다).
- 고려한 대안: 운영 관리자 화면에서 직접 수집·검수, 로컬 DB 파일 교체
- 결과와 트레이드오프: 세션 수정안 흐름을 그대로 쓴다. 통로를 새로 만들어야 하고, 운영 정기 수집이 만든 프로모션 후보와 로컬 승인본이 충돌하지 않게 하는 규칙이 필요하다.

## 2026-10-12: 스크립트로만 혜택을 보여 주는 카드사는 로컬 headless Chrome으로 원문을 수집

- 상태: 제안 — TASK-14 결정 대기 D5. 사용자 결정 전에는 구현하지 않는다.
- 맥락: 수집기는 공식 URL을 한 번 GET해 HTML·PDF 텍스트를 읽는다. 우리카드는 상품 페이지·상품공시실이 혜택과 상품안내장을 암호화된 요청으로 불러와 정적 원문이 없고, 케이뱅크·토스뱅크는 핵심 조건이 `<script>` 데이터나 클릭 뒤 화면에만 있다. TASK-14 대상 중 13장(우리 9, 케이뱅크 1, 토스 2, 네이버페이 1)이 여기에 걸린다. 설치된 Chrome의 headless `--dump-dom`으로 우리카드 상품 페이지를 그리면 혜택 전문이 나온다.
- 결정(제안): 허용 호스트에 한해 로컬 headless Chrome으로 렌더링한 DOM을 공식 원문으로 수집한다. 새 npm 의존성 없이 설치된 Chrome 경로를 환경 변수로 받는다. 렌더링이 필요한 출처는 로컬 카탈로그 작업과 정기 확인에서만 수집하고, 운영에는 TASK-06 통로로 승인본만 옮긴다.
- 고려한 대안: 호스트별 HTML 구조화 데이터 추출기(운영에서도 돌지만 우리카드와 클릭 뒤 내용을 못 읽음), 해당 카드를 데모 범위에서 제외
- 결과와 트레이드오프: 우리카드를 공식 원문 근거로 게시할 수 있다. Chrome이 없는 운영 서버는 이 출처의 원문 변경을 직접 감지하지 못하므로 로컬 정기 확인이 필요하고, 렌더링 결과가 시점마다 달라지지 않도록 카드사별 본문 범위가 필요하다.

## 2026-10-11: 카드 혜택은 사용자가 여는 AI 세션의 검토된 수정안으로 반영하고 카드 AI API 자동 구조화를 끈다

- 상태: 승인 — 사용자가 분담 방식과 주의점을 정하고 구현을 요청했다.
- 맥락: 카드 원문은 공지 후 반영까지 보통 한 달이 있고 자주 바뀌지 않는다. TASK-10의 결제 상황 분리, 공통 문구 분류, 근거 경로, 계산식 표현처럼 정교한 정리는 luna 자동 구조화가 해내지 못했고, 사용자와 대화하는 AI 세션과 결정론적 수정안 도구로 완성했다. 페이·통신사 프로모션은 매일 바뀌고 건수가 많아 자동 수집이 맞다.
- 결정: 카드 AI 상한 기본값을 0으로 바꿔 카드 수집은 공식 원문만 모아 비교한다. 원문이 바뀌면 게시 규칙을 새 원문으로 다시 검증한 결과를 `수정안 필요` 후보로 보관하고, 관리자 화면 배너와 정기 실행 종료 코드 2로 알린다. 사용자가 AI 세션을 직접 열면 `cards:sources`로 바뀐 원문을 비교하고 `cards:revise`로 수정안을 만들어 기존과 같은 근거 검증·audit·승인을 거친다. 구독형 AI는 사람이 연 세션에서만 쓰고 서버 정기 실행에 연결하지 않는다. 프로모션·SKT 보조 구조화는 기존 AI API 경로를 유지한다. 원문 변경을 사용자 화면에 따로 표시하지 않는다. 의미 hash는 카드사별 본문 범위만 비교해 메뉴·팝업·공지 목록 변화로 알림이 나지 않게 한다.
- 고려한 대안: 카드도 AI API로 계속 자동 구조화, 서버가 구독형 AI를 정기 호출, 원문 변경 기간에 사용자 화면에 확인 중 표시
- 결과와 트레이드오프: 카드 AI API 비용이 없어지고 정교한 정리를 같은 검증 관문으로 반영한다. 사용자가 세션을 열기 전까지는 이전 게시 규칙으로 계산하므로 공지 후 한 달 안에 반영해야 한다. `CARD_BENEFIT_BATCH_MAX_AI_CARDS`를 1 이상으로 두면 예전 자동 구조화를 다시 쓸 수 있다. 카드사가 본문 범위 표지를 바꾸면 전체 원문 비교로 돌아가 알림이 늘 수 있다. 위 `카드·프로모션 AI 모델을 luna로 고정` 결정은 프로모션과 다시 켠 카드 AI에만 적용된다.

## 2026-10-11: 두산 결제 상황은 선택만으로 확정하고 KB 공통 승인 문구는 실사용 검증 전까지 조건에서 제외

- 상태: 승인 — 사용자가 두산 게시 방식을 정했다.
- 맥락: 결제 상황(`purchaseScenario`)은 질문 1개 이상을 확인해야 확정되는 계약이었다. 두산 티켓·굿즈와 구장 F&B는 사용자가 상황을 직접 고르는 구매라 질문이 반복 확인에 그친다. KB 카드 공통 업종 분류·PG 승인 문구를 모든 혜택의 조건으로 두면 편의점·OTT·배달까지 모두 `조건 충족 시`가 된다.
- 결정: 사람이 검토한 수정안에서는 질문 없는 결제 상황을 허용해 선택을 확인으로 보고, 공식 범위·제외는 안내 문구(`notes`)로 표시한다. AI 후보는 여전히 질문을 1개 이상 내야 한다. KB 공통 업종 분류·PG 승인 문구는 사용자가 실사용으로 검증할 때까지 조건으로 두지 않고, 카드 전체 입점 매장 제외는 카드 주의 문구로 안내한다.
- 결과와 트레이드오프: 두산 혜택이 확정 순위에 들어간다. 시범경기 티켓이나 구장 GS25처럼 공식 제외 대상에서 상황을 고르거나 PG·입점 매장으로 승인되면 과대 계산될 수 있다. 실사용 검증 결과에 따라 문구를 조건으로 되돌릴 수 있다.

## 2026-09-12: 기본 실적은 자동 반영하고 카드별 명시 제외만 적용
