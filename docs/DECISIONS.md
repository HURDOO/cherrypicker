# Cherrypicker 결정 기록

이 문서는 되돌리기 비싸거나 제품 전반에 영향을 주는 결정만 기록한다. 작은 구현 선택과 일회성 작업 메모는 `docs/TASKS.md`와 코드에서 관리한다.

## 2026-09-04: 비로그인 local-first를 기본 사용 모델로 유지

- 상태: 승인
- 맥락: 결제 직전에 빠르게 사용해야 하므로 로그인을 선행 관문으로 두면 핵심 가치가 약해진다. 개인 카드·실적·거래 기록은 공용 혜택 카탈로그와 성격이 다르다.
- 결정: 일반 사용은 로그인 없이 작동하고 개인 workspace를 브라우저 origin별 IndexedDB에 저장한다. 계정은 백업·복원·다중 기기 동기화를 원하는 사용자에게만 제공한다. 로그인과 동기화가 로컬 데이터를 자동으로 덮어쓰거나 삭제하지 않는다.
- 고려한 대안: 로그인 필수 서버 데이터, 완전한 로컬 전용, 로그인 시 서버 데이터로 즉시 전환
- 결과와 트레이드오프: 첫 사용 마찰과 서버 개인정보 범위가 줄어든다. 반면 카카오톡 내 브라우저, Chrome·Safari와 서비스 주소가 다르면 로컬 데이터가 분리될 수 있어 사용자 안내와 선택적 백업이 중요하다.

## 2026-09-04: 첫 설정에서 카드 외 정보를 선택 입력으로 처리

- 상태: 승인
- 맥락: 실적을 알기 위해 은행 앱을 왕복하는 과정은 새로고침과 이탈을 유발할 수 있고, 결제 직전 추천의 가치를 보기 전에 너무 많은 설정을 요구하면 첫 사용을 막는다.
- 결정: 짧은 서비스 소개를 첫 화면으로 두고, 카드·혜택·실적·즐겨찾기·첫 추천을 고유 URL로 나눠 브라우저 히스토리와 진행 상태를 함께 유지한다. 카드를 하나 이상 선택하면 첫 추천으로 진행할 수 있게 하며, 실적, 멤버십·페이·구독·포인트와 즐겨찾기는 건너뛰고 나중에 보완할 수 있어야 한다. 통신사 멤버십을 선택한 경우에는 등급별 금액 차이를 정확히 계산하도록 등급까지 함께 받는다. 작성·저장한 내용은 외부 앱 왕복·새로고침 후에도 유지하고, 마지막 추천은 멤버십·구독·페이·카드의 전체 조합에서 놓치고 있던 혜택 브랜드와 예시 금액을 보여준 뒤 브랜드 선택·금액 입력·혜택 공개를 튜토리얼처럼 안내한다.
- 고려한 대안: 모든 설정 필수, 실적만 필수, 별도 온보딩 없이 긴 설정 페이지만 제공
- 결과와 트레이드오프: 2~3분 안에 첫 가치를 볼 수 있지만, 생략한 정보로 인해 혜택이 보수적으로 계산되거나 조건 확인이 더 필요할 수 있다.

## 2026-09-04: 미지원 브랜드에 일반 결제 추천을 제공

- 상태: 승인
- 맥락: 실제 결제처를 모두 브랜드 카탈로그에 선등록할 수 없고, 일반 적립·실적 관점의 카드 비교는 여전히 가치가 있다.
- 결정: 브랜드 검색 결과가 없거나 사용자가 직접 선택하면 `일반 결제 추천`으로 진입한다. 특정 브랜드·카테고리 전용 혜택은 제외하고 일반 적용 규칙만 비교한다.
- 고려한 대안: 미지원 브랜드에서 추천 차단, 사용자가 매번 커스텀 브랜드를 먼저 추가, 모든 브랜드 전용 규칙을 가능성으로 표시
- 결과와 트레이드오프: 사용 가능 결제처 범위가 넓어지고 카탈로그 등록 마찰이 줄어든다. 반면 브랜드 전용 혜택을 잘못 섞지 않도록 도메인 계약과 회귀 테스트가 필요하다.

## 2026-09-04: 혜택 금액을 보수적으로 표시하고 실적 우선을 보조 판단으로 제공

- 상태: 승인
- 맥락: 실적 증가액을 큰 혜택 숫자처럼 표시하면 이번 결제의 실제 할인으로 오인할 수 있고, 자동이체·특정 상품·승인 경로 같이 앱이 알 수 없는 조건을 확정으로 계산하면 과대 추천이 된다.
- 결정: 큰 숫자는 이번 결제의 실제 혜택만 나타낸다. 혜택은 `확정`, `조건 충족 시`, `정보 제공`으로 구분하고 확정 혜택을 기본 순위로 삼는다. 즉시 혜택이 없거나 소액 기준보다 작을 때만 실적 추천을 우선해 보여줄 수 있다. 소액 기준 기본값은 100원이며 사용자가 바꾼다.
- 고려한 대안: 예상 최대 금액으로 모든 혜택 순위화, 실적 가치를 즉시 혜택에 합산, 조건부 혜택을 순위에서 완전히 제외
- 결과와 트레이드오프: 큰 숫자의 신뢰와 과대 추천 방지를 우선한다. 일부 혜택은 사용자의 조건 확인 전에 확정 가치로 보이지 않으며, 실적 추천은 보조 문구와 진행 정보를 필요로 한다.

## 2026-09-04: 공식 원문, AI 후보와 사람 검수를 분리

- 상태: 승인
- 맥락: 카드·프로모션 문서는 길고 형식이 다양해 AI 구조화가 유용하지만 누락·잘못된 필드·속이 다른 근거가 발생할 수 있다.
- 결정: 공개 공식 페이지·API·PDF를 우선 출처로 삼고 원문·URL·수집 시각·version·hash를 보존한다. AI는 전수 혜택 인벤토리와 구조화 후보를 만들지만 게시 권한을 갖지 않는다. schema, 인용, 참조, 숫자·한도·diff를 검증하고 승인된 revision만 공개한다. 삭제·조건 제거·한도 증가 등 고위험 변경은 명시적 검수를 유지한다.
- 고려한 대안: 카드사별 수동 parser만 사용, AI 결과 자동 게시, 최신 원문으로 기존 혜택 즉시 교체
- 결과와 트레이드오프: 다양한 문서 형식으로 확장하면서도 기존 게시본을 보호한다. 반면 원문 보존, 감사, 검수 UI·revision의 복잡도와 사람 검수 비용을 감수한다.

## 2026-09-04: 초기 비공개 베타는 직접 피드백으로 운영

- 상태: 승인
- 맥락: 초기 대상은 소유자와 직접 연락할 수 있는 3~4명이고, 고정된 기간·수치보다 실제 반복 사용의 문제를 빠르게 고치는 것이 우선이다.
- 결정: 첫 베타는 주로 20대 대학생 지인 3~4명을 지원 카드 기준으로 초대한다. 오류·없는 카드·추천 피드백은 소유자에게 카카오톡으로 직접 받고, 행동 테레메트리·앱 내 제보 폼·공개 사용자용 개인정보 문서는 추가하지 않는다. 사용자가 만족할 때까지 반복 개선한 뒤 오픈 베타를 별도 승인한다.
- 고려한 대안: 처음부터 공개 베타, 분석 SDK·공식 폼·Discord 서버를 선구축, 고정된 베타 종료일 지정
- 결과와 트레이드오프: 초기 범위·개인정보·관측성 복잡도가 줄어든다. 반면 자동 정량 지표와 공식 지원 창구가 없으므로 소유자가 피드백과 문제 기록을 직접 관리해야 한다.

## 2026-09-04: 비공개 베타의 수집 주기·AI 비용·백업 범위

- 상태: 승인
- 맥락: 카드는 변동이 비교적 적고 페이·통신사 프로모션은 당일 행사가 많다. 개발 중 충전한 OpenAI credit이 빠르게 소진되었고, 초기 베타에 완전한 운영 인프라를 미리 만들 필요는 없다.
- 결정: 카드는 주 1회, 프로모션은 매일 새벽·아침에 외부 스케줄러로 확인한다. 원문 의미 hash가 같으면 AI를 재호출하지 않고 배치 상한을 유지한다. 2026-09-04 기준 남은 초기 $5 credit은 $3.36이며, 비공개 베타 전에는 가능하면 추가 충전하지 않는다. 장애 알림은 Discord webhook을 사용하되 URL은 구현 직전에 받는다. 새 상시 외부 백업 체계는 베타 전에 추가하지 않고, 이미 구현된 배포 전 snapshot·backup·verify·restore 절차는 유지하여 1회 검증한다.
- 고려한 대안: 모든 출처를 매일 AI로 재구조화, 카드와 프로모션을 같은 주기로 수집, 베타 전 외부 복제·보존 서비스 추가, 알림 없이 수동 상태 확인
- 결과와 트레이드오프: 변경 감지 신선도와 AI 비용을 분리할 수 있다. 외부 스케줄러·webhook 구성이 필요하고, 베타 기간에 서버 디스크 장애가 나면 외부 복제로 복구하지 못할 위험을 한정된 범위에서 수용한다.
