# Cherrypicker 결정 기록

이 문서는 되돌리기 비싸거나 제품 전반에 영향을 주는 결정만 기록한다. 작은 구현 선택과 일회성 작업 메모는 `docs/TASKS.md`와 코드에서 관리한다.

## 2026-09-16: main 통합과 Cherrypicker 주소 전환

- 상태: 승인 — 브랜치 통합과 목표 주소. 실제 운영 데이터 이전·migration·대시보드 적용은 미실행.
- 맥락: 사용자가 장기간 유지한 `promotion` 작업을 `main`에 합치고 서비스 도메인도 `cherrypicker`로 바꾸도록 요청했다. 단기 목표는 한 달 이내 본인·지인의 실사용 도구, 장기 목표는 약 세 달 안에 외부 사용자와 수익화를 고려하는 창업학회 아이템이다.
- 결정: 기존 작업과 양쪽 Git 이력을 보존해 `main`으로 통합한다. 배포 목표는 `cherrypicker`와 `https://cherrypicker.app.hurdoo.kr`로 정하고 이미지 저장소는 `ghcr.io/hurdoo/cherrypicker`를 유지한다. 인증 origin은 실행 시 제공되는 주소를 사용한다.
- 경계: 현재 deployd는 등록된 앱의 ID·hostname 변경을 지원하지 않는다. 신규 등록 또는 플랫폼 전환이 필요하며 기존 운영 DB·계정·검수 revision과 브라우저 workspace를 빈 데이터로 대체하지 않는다. 기존 주소·앱은 데이터 보존과 새 주소 검증 전까지 유지한다. 자세한 전환과 미완료 항목은 `docs/cherrypicker-domain-transition.md`와 TASK-11에서 관리한다.
- 미확정: 수익 모델, 공개 베타 시점, 운영 DB의 구체적 이전 방법은 승인된 구현 상태로 간주하지 않는다.

## 2026-09-12: 기본 실적은 자동 반영하고 카드별 명시 제외만 적용

- 상태: 승인
- 맥락: 카드별 제외 문구가 아직 구조화되지 않았다는 이유만으로 모든 새 거래를 `UNKNOWN`·0원 처리하면 기록 후 실적이 자동 누적되지 않아 핵심 사용 흐름이 무너진다. 직전 변경은 사용자의 카드별 예외 의도를 지나치게 보수적으로 해석했다.
- 결정: 기본값은 카드 승인금액 전액을 예상 실적에 자동 반영한다. 카드별 공식 페이지·약관에 명시된 제외 조건이 데이터 규칙으로 등록되고 해당 거래에서 실제로 판정될 때만 전체 또는 해당 범위의 실적을 제외한다. 정책이 없는 게시 카드·커스텀 카드·catalog v2에도 같은 기본값을 적용하며 다른 카드의 제외 규칙을 공통 적용하지 않는다. 명시적인 거래 종류가 입력되지 않은 보통 결제는 일반 거래로 간주한다. 사용자 수동 입력은 카드사 수치 보정용 선택 기능이고 자동 기록의 필수 단계가 아니다. 과거 거래 snapshot은 소급 변경하지 않는다.
- 고려한 대안: 카드별 정책 전수 검수 전까지 모두 0원, 모든 카드에 같은 제외 규칙 적용, 매 결제마다 사용자가 실제 실적을 입력
- 결과와 게이트: 직전의 `미검증이면 모두 0원` 변경을 철회한다. 특정 거래 종류(무이자할부·상품권 등)를 자동 제외하려면 앱이 그 종류를 식별할 입력·신호가 필요하다. 아직 식별할 수 없는 예외를 자동 처리했다고 간주하거나 두산 후보의 금액 영향 미지원 문구를 제거하지 않는다.

## 2026-09-12: 카드별 실적 제외 조건을 공통 기록 계약으로 표현

- 상태: 승인
- 맥락: 두산베어스 KB카드 공식 상품 페이지는 카드 할인 적용 거래의 매출 전체를 전월 이용실적에서 제외한다. 현재 로컬 기록은 결제 승인금액을 실적 기여액으로 더해 다음 달 목표와 추천 실적을 과대 표시할 수 있다.
- 결정: 카드 ID별 예외 코드 대신 공식 인용이 붙은 versioned 실적 제외 규칙을 카드 데이터에 둔다. 카드 자체의 확정 할인 적용 거래는 매출 전체를 0원으로, 할인 적용 여부처럼 실제로 판정 중인 조건은 실적 기여를 `UNKNOWN`·0원으로 처리해 실적 우선 추천을 부풀리지 않는다. 추천·로컬 기록·계정 기록은 같은 순수 계산기를 사용하고, 0원도 당시 판정·근거와 함께 기록한다. 정책이 없는 기존 게시 카드·catalog v2는 승인금액 기준 예상 실적을 유지한다. 실제 카드사 확정 실적은 사용자가 선택적으로 수동 보정할 수 있으며 앱의 기록은 카드사 명세서가 아닌 예상치다.
- 고려할 대안: 모든 거래 전액 실적 반영 유지, 모든 거래 0원 처리, 실적은 사용자가 매월 수동 입력만 하도록 전환, 카드별 조건문 추가
- 결과와 게이트: 공통 정책 경로와 0원 snapshot은 구현했지만 실제 두산 후보에는 아직 적용하지 않았다. 공식 제외 항목 전수 대응, 실제 후보 재검수, 할인받은 결제→기록→다음 달 재계산 검증 전에는 두산 후보의 금액 영향 `unsupportedClauses`를 제거하거나 게시하지 않는다.

## 2026-09-12: 실제 결제처와 구매 상황을 분리하고 미확인 사실은 조건부로 표시

- 상태: 승인
- 맥락: 두산 홈경기 티켓·굿즈와 구장 F&B는 한 개의 상점이 아니라 상품·경기·장소·판매 경로·제외 매장이 결합된 적용 범위다. `야구 홈경기 티켓/굿즈`, `홈구장 내 F&B`를 공개 브랜드로 만들면 내부 참조 검사는 통과해도 사용자가 실제 가맹점이라고 오인하거나 혜택을 과대 계산할 수 있다.
- 결정: 공개 브랜드 registry에는 실제 식별 가능한 결제처만 넣는다. 판매처가 아닌 적용 범위는 카드 DSL의 `purchaseScenario`로 표현하고, 사용자가 해당 상황을 명시적으로 선택했을 때만 매칭한다. 공식 조건 중 앱이 관측하지 못하는 사실은 구체적인 `requiredChecks`로 제시하며 확인 전 혜택은 조건부이고 기본 확정 순위에 넣지 않는다. AI는 공식 문서 기반 후보와 질문을 제안할 수 있지만 검수 없이 게시하거나 사용자가 제공하지 않은 구매 사실을 확정하지 않는다. 새로운 사실 종류는 카드별 예외 코드가 아닌 공통 입력 계약으로만 확장한다.
- 고려한 대안: 두 개의 가상 공개 브랜드 등록, 결제처 이름만으로 행사·상품 자동 추정, 모든 상황 혜택을 0원 정보로 유지, 결제 때마다 AI가 자격을 판정
- 결과와 트레이드오프: 결제처 검색과 상황 검색을 구분해 의미 오염을 막는다. 상황 선택 뒤에도 질문 확인이 필요하고, 계정 서버의 레거시 거래 경로는 브랜드 ID를 필수로 요구하므로 첫 상황 기록은 로컬 workspace에 한정한다. 두산 실제 후보는 재구조화·사람 검수·별도 게시 승인 전까지 `PENDING`과 `DRAFT`를 유지한다.

## 2026-09-07: 카드 혜택을 허용 목록 기반의 결정론적 DSL로 확장

- 상태: 승인
- 맥락: 현재 AI는 코드가 미리 정의한 `BenefitRule` 필드만 채울 수 있다. 두산베어스 KB카드의 신규회원 월 한도 50%처럼 모델 밖 의미가 나오면 정확히 구조화할 수 없고, 카드마다 TypeScript 분기를 추가하면 참여자 카드가 늘어날수록 유지보수와 회귀 위험이 함께 커진다.
- 제안: 카드 혜택을 versioned JSON AST로 표현한다. AI는 조건·산술·분기·기간 집계·한도·공유 범위·결제처 집합 등 애플리케이션이 허용한 연산자만 조합하고, 순수 TypeScript evaluator가 브라우저와 서버에서 동일하게 계산한다. 임의 코드·SQL·네트워크 호출은 허용하지 않는다. 기존 규칙과 과거 snapshot은 legacy adapter로 보존하고 새 후보부터 점진 적용한다. 허용 목록으로 표현할 수 없는 문구는 공식 근거와 함께 `unsupportedClauses`에 남기며, 금액에 영향을 주면 게시를 차단한다.
- 고려한 대안: 현재 고정 schema에 카드별 필드·분기를 계속 추가, AI가 JavaScript를 생성해 실행, 모든 새 카드를 정보 제공으로만 등록, 완전한 범용 규칙 언어를 한 번에 구축
- 예상 결과와 트레이드오프: 새 값·결제처·기존 의미의 새로운 조합은 코드 배포 없이 후보 데이터로 수용할 수 있고, AI 출력의 실행 범위를 검사·감사할 수 있다. 진짜 새로운 의미나 새로운 외부 데이터는 여전히 DSL 연산자 또는 입력 계약을 한 번 확장해야 하며, 초기에는 legacy와 DSL의 이중 해석·catalog 호환·검수 UI 복잡도를 감수한다.

## 2026-09-07: 현재 테스트 카드로 베타 준비를 검증하고 참여자 카드는 시작 직전에 추가

- 상태: 승인
- 맥락: 비공개 베타 참여자가 아직 확정되지 않아 사전 카드 목록이 없고, Cherrypicker는 신규 카드 발급을 추천하는 서비스가 아니라 사용자가 이미 보유한 카드를 잘 쓰도록 돕는 서비스다.
- 결정: TASK-04는 현재 테스트 카드 14장과 신규 카드 요청 1건의 수집·구조화·검수·게시 경로를 검증한다. 실제 참여자의 카드는 각 참여 시작 직전에 조사하고, 없는 카드는 같은 관리자 경로로 동적으로 추가하거나 근거 부족 사유를 명확히 남긴다. 카드의 발급 중단 여부는 운영 기록으로 보존하되 이미 보유한 카드의 선택 가능 여부, 추천 순위 또는 사용자 경고에 사용하지 않는다.
- 고려한 대안: 참여자 전체를 먼저 모집해 카드 목록을 T4 선행 조건으로 확정, 발급 중단 카드를 사용자 화면에서 경고하거나 숨김, 모든 예상 카드를 베타 전에 미리 수집
- 결과와 트레이드오프: 참여자 모집을 기다리지 않고 현재 데이터로 정확성과 운영 절차를 검증할 수 있고 보유 카드 중심 제품 원칙을 유지한다. 대신 참여자별 카드 지원은 베타 시작 직전에 반복 수행해야 하며, 게시 또는 보류 판정이 끝나기 전에는 해당 참여자의 핵심 흐름 검증을 시작하지 않는다.

## 2026-09-04: 비로그인 local-first를 기본 사용 모델로 유지

- 상태: 승인
- 맥락: 결제 직전에 빠르게 사용해야 하므로 로그인을 선행 관문으로 두면 핵심 가치가 약해진다. 개인 카드·실적·거래 기록은 공용 혜택 카탈로그와 성격이 다르다.
- 결정: 일반 사용은 로그인 없이 작동하고 개인 workspace를 브라우저 origin별 IndexedDB에 저장한다. 계정은 백업·복원·다중 기기 동기화를 원하는 사용자에게만 제공한다. 로그인과 동기화가 로컬 데이터를 자동으로 덮어쓰거나 삭제하지 않는다.
- 고려한 대안: 로그인 필수 서버 데이터, 완전한 로컬 전용, 로그인 시 서버 데이터로 즉시 전환
- 결과와 트레이드오프: 첫 사용 마찰과 서버 개인정보 범위가 줄어든다. 반면 카카오톡 내 브라우저, Chrome·Safari와 서비스 주소가 다르면 로컬 데이터가 분리될 수 있어 사용자 안내와 선택적 백업이 중요하다.

## 2026-09-04: 첫 설정에서 카드 외 정보를 선택 입력으로 처리

- 상태: 승인
- 맥락: 실적을 알기 위해 은행 앱을 왕복하는 과정은 새로고침과 이탈을 유발할 수 있고, 결제 직전 추천의 가치를 보기 전에 너무 많은 설정을 요구하면 첫 사용을 막는다.
- 결정: 짧은 서비스 소개를 첫 화면으로 두고, 카드·혜택·실적·즐겨찾기·첫 추천을 고유 URL로 나눠 브라우저 히스토리와 진행 상태를 함께 유지한다. 카드를 하나 이상 선택하면 첫 추천으로 진행할 수 있게 하며, 실적, 멤버십·페이·구독·포인트와 즐겨찾기는 건너뛰고 나중에 보완할 수 있어야 한다. 통신사 멤버십을 선택한 경우에는 등급별 금액 차이를 정확히 계산하도록 등급까지 함께 받는다. 작성·저장한 내용은 외부 앱 왕복·새로고침 후에도 유지하고, 마지막 추천은 멤버십·구독·페이·카드의 전체 조합에서 놓치고 있던 혜택 브랜드와 예시 금액을 보여준 뒤 브랜드 선택·금액 입력·혜택 공개를 튜토리얼처럼 안내한다.
- 고려한 대안: 모든 설정 필수, 실적만 필수, 별도 온보딩 없이 긴 설정 페이지만 제공
- 결과와 트레이드오프: 2~3분 안에 첫 가치를 볼 수 있지만, 생략한 정보로 인해 혜택이 보수적으로 계산되거나 조건 확인이 더 필요할 수 있다.

- 결과와 트레이드오프: 변경 감지 신선도와 AI 비용을 분리할 수 있다. 외부 스케줄러·webhook 구성이 필요하고, 베타 기간에 서버 디스크 장애가 나면 외부 복제로 복구하지 못할 위험을 한정된 범위에서 수용한다.
